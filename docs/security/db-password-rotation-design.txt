Companion files on branch codeguard: script/rotate_db_password.pl, t/rotate_db_password_dryrun.t, docs/security/db-rotation.example.json
Builds on: secrets-design.txt, key-rotation-plan.txt, db-consolidation-plan.txt (same folder). No values appear in this file.

PROBLEM
Shanta wants one action that changes the primary database password in the databases, in the secrets file on every server, and in the
running apps, in an order that keeps load balancing and failover working. Today a password change is a manual, partial job:
the old password is spread over many files and logins, and nothing changes the servers, the files and the apps together.

IMPACT
- A hand rotation across 3+ servers and 2+ app nodes will leave one of them on the old password: the app then silently falls back to
  another login, or to SQLite, or fails at the next restart. The old, leaked password keeps working on any server we forget.
- A second failover/load server multiplies every step. The sequence has to be a list in a config file, not knowledge in someone's head.

SOLUTION  (plain words; the script is the same steps in code)
Rule: ONE database password lives in ~/.comserv/secrets (the primary app login). Every other credential (comserv_admin, forager,
postgres, backup logins) goes into encrypted app_secrets rows (key_version) and leaves the dbi files. The app is the broker; the rotation
tool reads the DB-admin login it needs from a root-only option file today and from app_secrets once Phase 3 exists.

A. Why two logins during the change
MariaDB (10.6 here) cannot keep "old and new password" on one account. So the primary login is a PAIR of names (config "logins":
comserv_app and comserv_app_b). The new password goes on the idle partner. The old login is not touched. Both work at the same moment.
The files then say: NEW login priority 1, OLD login as a lower-priority fallback slot (<slot>_prev). Any node not yet restarted still runs on
OLD; a restarted node runs on NEW and would fall back to OLD if NEW broke. The next rotation simply swaps the roles.

B. The sequence (script phase "rotate"; every step has an undo; the numbers match the dry-run output)
 0. Preflight, read-only: config valid and mode 600; master key dir exists and is 700; admin login works on every DB server; every app node
    answers ssh and its health check; at least one node can be drained while another stays healthy; a lock file prevents two runs.
 1. snapshot       copy each node's secrets file to <file>.pre-rotate.<run> (mode 600). This is the exact rollback source.
 2. pick-logins    find the OLD login = the first listed login that logs in on EVERY DB server. Today that is shanta_forager (comserv_app fails).
                   NEW = the partner of OLD, or comserv_app when OLD is not in the pair (the one-time adoption, see section D).
 3. new-password   read it from a mode-600 file you provide, or generate 32 chars from /dev/urandom (letters, digits, _ . - only).
                   Held in memory; with --generate it is kept in a 600 file in the state dir until retire, never printed.
 4. stage-db:<S>   on each DB server (primary first; a replica that replicates accounts is skipped): CREATE USER IF NOT EXISTS + ALTER USER
                   on the NEW login with the new password, then the grants from config. OLD untouched. Undo: set NEW to a random password.
 5. verify-new-login   NEW + new password must run verify_sql on EVERY server before any file changes. One failure stops here.
 6. roll-node:<N>  one node at a time: drain from the balancer (config drain_cmd) -> write the file atomically (NEW primary, OLD fallback)
                   -> restart (restart_cmd) -> wait for health -> check the DB shows connections as NEW from that node -> undrain.
                   The next node starts only when this one is healthy, so min_healthy_nodes stay serving. Undo: restore the snapshot, restart.
 7. soak           re-run every node's health check for soak_seconds (default 300). Any failure rolls everything back.
 8. save-state     record names and run id only. Old login STILL works. The tool stops and tells Shanta to watch the apps.
Phase "retire" (separate command, run when Shanta is satisfied, same day or next):
 R1. health gate   all nodes healthy and no connection from the OLD login on any server.
 R2. retire-db     set the OLD login to a random unknown password on every DB server (account kept, so next rotation can reuse it).
 R3. retire-files  remove the fallback slot and every slot still using the OLD login from every node file (atomic).
 R4. prove-old-dead  the OLD login with its old password must now FAIL on every server; apps still healthy.
 R5. purge snapshots (they held the old password) and the staged new-password file.
After retire the secrets file holds ONE login and ONE password. This is the only step that cannot be undone, which is why it is separate.

C. Dry-run, health check, rollback, audit
- Dry-run is the default. With no flags it reads the config, checks permissions, prints the numbered plan, connects to nothing, reads or
  generates no password and writes nothing. --check-remote adds read-only logins and pings. Only --execute changes anything.
- Automatic rollback: if any step fails, completed steps are undone in reverse order (a half-rolled node is restored inside its own step).
  Phase "rotate" never touches the OLD login, so rollback always lands on a working system.
- Health = the config health_cmd per node (curl to the app, plus the connection check in step 6).
- Audit log: ~/.comserv/logs/db-rotation-audit.jsonl (mode 600), one JSON line per step: time, run id, OS user, step, target name, result.
  No passwords, no hashes, no file contents. Later the same lines also go into the app's log table so they show on the admin page.

D. Per-server and per-node lists (the "second server" mechanism)
One config file, ~/.comserv/secrets/db-rotation.json (600, no passwords; example: docs/security/db-rotation.example.json):
  db_servers : name, host, port, admin_defaults_file (root-only my.cnf with an account that may CREATE/ALTER USER), account_hosts, and
               replicates_from when accounts replicate from another server (DDL then runs once, on the source).
  app_nodes  : name, ssh (omit for this machine), secrets_dir, drain_cmd/undrain_cmd (balancer), restart_cmd, health_cmd.
Adding the failover/load server later = add one entry to each list and run --check-remote. Include the NATIVE MariaDB (127.0.0.1:3306) and
the dev/ZeroTier servers until db-consolidation-plan.txt retires them, otherwise the old password still opens them.
Kubernetes later: only restart_cmd/health_cmd change (kubectl rollout restart) and the file push becomes a Secret update.

E. The two logins Shanta has today (shanta_forager vs comserv_app)
First run is an "adoption". comserv_app exists on :3307 but its stored password is wrong, so the app falls back to shanta_forager.
The script treats shanta_forager as OLD (it logs in everywhere), sets a fresh password on comserv_app (limited DML grants from config),
moves the app to comserv_app, and at retire makes shanta_forager's password random and removes every slot that used it. After that the
files hold one login. Remaining steps are outside the script: move comserv_admin/postgres/backup values into app_secrets, drop the
shanta_forager account after the hold, and make shanta_forager dbi entries vanish from the 9 other files (use db-consolidation-plan.txt).
Small code change needed before the first real run: DBEncy.pm only treats the literal name comserv_app as primary; change the test to the
pair (comserv_app, comserv_app_b) from config. Controller/RemoteDB change_password should call this tool instead of ALTER USER USER() alone.

RISK / UNDO
- Before retire: any failure rolls back automatically; manual undo = copy each <file>.pre-rotate.<run> over the file and restart that node.
  Old login, old password and old files stay valid, so nothing is lost.
- The password exists in memory, in the node files, and (until retire) in the 600 staged file and snapshots. Not in argv, env, logs or
  the audit file. ssh stdin is used to push files. ssh uses keys (BatchMode); SSHPASS from deploy.sh is honoured if set.
- Risks: the admin option file is one more root-only secret until Phase 3 (delete it after the run); a restart is a short blip per node,
  which is why drain + one-at-a-time + health gate exist; a server missed in db_servers keeps the old login alive (the dry-run lists every
  server it will touch; compare to `ss -ltn` on db hosts); replicated accounts must be flagged replicates_from or DDL runs twice (harmless).
- Retire is final for the old password. Keep a 1-2 day hold between rotate and retire.
- Rotating does NOT remove the old password from git history, forks, clones, caches or backups. It only makes that password useless, which
  is what actually closes the leak; the branch/history plan is in branch-cleanup-plan.txt.
- Not done in the skeleton (stated, not hidden): PostgreSQL login, app_secrets as the admin source, an app-UI trigger, balancer API calls
  (drain_cmd/undrain_cmd are your commands), and the live --execute path has only been exercised by unit tests of the file edits, never
  against a database. Rehearse on dev first.
