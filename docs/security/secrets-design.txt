COMSERV SECRETS DESIGN  (Code Guard for Shanta, 2026-10-20)  -- add this to the server-room plan

PROBLEM
Secrets live in four places with no single owner: tracked .env files, config files in the repo
(nginx NPM token, proxmox_credentials.json, until now the encryption key files), loose files in
~/.comserv (some world-readable), and GitHub Secrets. Bots, Hermes, scripts and people all read
them directly. Any copy of the repo or any bot with shell access has every credential.
The code also silently invented a new encryption key when none was found, which quietly breaks
every stored password.

EVIDENCE
- Tracked since Oct 2025: .env, .env.development, .env.production, Comserv/.env.staging with
  literal DB, DB root, ENCY, Redis, SMTP passwords and a staging API key; .env.example also had real-looking values.
- Comserv/config/nginx/npm-{development,staging,production}.conf contain the NPM JWT api_key.
- Comserv/config/proxmox_credentials.json (encrypted token) and the mail/proxmox key files were
  both in git from 2026-05-02, so the ciphertext and the key were public together.
- ~/.comserv/secrets and secrets/dbi were 775, several files 664.
- The security audit page already asked for this cleanup; it was never done.

IMPACT
Anyone with repo access (GitHub, any clone, any bot) can log into the databases, Redis, SMTP,
NPM and Proxmox. Adding users or a second server multiplies the copies.

SOLUTION
1. Root secrets only, outside git.
   Exactly two kinds of secret live on disk: the primary DB login(s) the app needs to start, and the
   master encryption key(s). Layout, identical on every node:
     <COMSERV_SECRETS_DIR, default ~/.comserv/secrets>   700, files 600  (dbi/*.json = DB logins)
     <COMSERV_KEY_DIR,     default ~/.comserv/keys>      700, files 600  (.<ns>_encryption_key)
   Containers mount both read-only (/home/comserv/.comserv/secrets, /opt/comserv/keys) and get
   COMSERV_KEY_DIR from the compose file. Paths are always env-driven; $HOME is only a fallback.
2. Everything else in the database, encrypted.
   SMTP, Redis, NPM, Proxmox, mailbox passwords, third-party API tokens go into one table, e.g.
   app_secrets(name, scope/site, ciphertext, key_version, created_by, rotated_at). key_version lets
   a new master key be introduced while old rows still decrypt; a rotation job re-encrypts rows and
   bumps the version. (user_mailboxes.password_enc and UserApiKeys move here or gain key_version.)
3. The app is the only reader.
   Bots, Hermes and users never read secret files. They call an authenticated app API with their own
   token (one per bot, one per user), role-checked (e.g. bot:ai-eval may read only its own token;
   admin may rotate), and every read/write/commit request is logged (who, what name, when, from where;
   never the value). Git commits by bots also go through the app API (Util/Git.pm), so the hooks and
   secret guard always run.
4. Fail loudly.
   The app refuses to start (and Encryption.pm dies) if a required key or DB login is missing.
   New keys are only created on purpose: COMSERV_KEY_DIR=... script/generate_encryption_key.pl <ns>.
5. Growth and a second server.
   - Multi-user: per-user tokens and roles from day one; secrets are scoped by site.
   - Second node (failover/load): both nodes use the same shared or replicated database, so the
     encrypted secrets table travels with it. Each node gets the SAME root-secret layout, copied
     once over SSH (never via git), same paths, same env names. Nothing is node-specific except paths
     supplied by env.
   - Later, only the root-secret SOURCE changes: a Kubernetes Secret mounted at the same paths
     (/var/run/secrets/comserv or COMSERV_KEY_DIR), or Vault/OpenBao/SOPS rendering the same files.
     The app code does not change.

PHASED MIGRATION
Phase 0 (done on branch codeguard): untrack key files, .env*, NPM conf, proxmox JSON (copies in
  ~/.comserv/secrets/repo-untracked, 600); lock perms 700/600; Encryption.pm fails loudly;
  dev/staging compose mount keys+secrets read-only; stricter gitleaks + CI.
Phase 1 (rotate, production first): see key-rotation-plan.txt. Prod DB + root, prod ENCY, prod
  Redis, SMTP, NPM JWT, Proxmox token, mailbox passwords, staging API key, then dev/staging DB.
  Turn on GitHub secret scanning + push protection.
Phase 2: prod compose/deploy.sh also mount ~/.comserv/keys:ro + COMSERV_KEY_DIR; app startup check.
Phase 3: app_secrets table + key_version + admin UI; move SMTP/Redis/NPM/Proxmox/API tokens in.
Phase 4: per-bot/per-user API tokens, role checks, audit log; switch Hermes and bots to the API;
  remove their direct file access (hd_token_secret, ai_eval_ingest_token, supergrok_oauth, credentials).
Phase 5: second node with the same layout; optional k8s Secret / Vault as root-secret source.
Phase 6 (optional, after rotation): purge old secrets from git history (filter-repo + force push).

RISK / UNDO
- Missing key now stops the app instead of corrupting data. Undo: set COMSERV_ALLOW_KEYGEN=1 (not recommended).
- Untracked files stay on disk; pulling the change on another checkout may delete them there.
  Copies are in ~/.comserv/secrets/repo-untracked/ (restore with cp).
- Compose changes are two volume lines and one env line per file; revert the commit to undo.
- Rotation cannot be undone, but each credential is independent; keep old values until verified.
- Lose the master key = lose every encrypted secret: keep two offline backups of ~/.comserv/keys.
